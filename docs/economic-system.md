# 地精经济系统：设计与算法

本文是 `forever` 分支的实现说明。它回答三个问题：系统把什么当作事实、如何从事实得到行动、哪些结论不能从客户端数据里得到。

## 1. 本体与十条不变量

系统的主语不是“物品价格”，而是**玩家的经济行动**：

```text
事件 → 状态 → 决策 → 行动 → 学习
```

十条不变量：

1. 决策单位是头寸/行动/论点，不是雷达行。
2. 目标函数显式：风险调整后的真实金币/真实分钟，受资金、背包、冷却、注意力约束。
3. 需求标签来自自己的成交/竞价/实验；公共消失只是区间先验。
4. 生产网络 = 配方图 + 容量约束 + 影子价格。
5. 竞争 = 对手图 + 市场影响 + 反射性。
6. 信念状态带不确定性，并主动设计实验。
7. 执行 = 游戏内驾驶舱 + 条件策略 + 人工确认。
8. 决策核心只有一份，游戏内与桌面共用 `Core.lua`。
9. 名义价格 deflate 到真实/相对价格。
10. 运行可靠性：数据新鲜、失败降级、扫描不丢。

## 2. 数据契约

桌面端的每一次读取都按 `Market`（realm + faction）隔离：默认取最新扫描所属市场，
可用 `AQT_MARKET="realm|faction"` 固定。快照、日线、头寸、成交、决策都不会跨市场合并。

### 2.1 `WoWderhoiAH_ScanData`（v4）

一次全量扫描的最新快照：

- 元数据：`dataVersion`、`scannedAt`、`server`、`faction`、`character`、`cash`、`total`。
- `items[itemId]`：名称、品质、物品类别、市场类型（`marketType`：`commodity` | `item`，
  扫描时按当时的物品记录判定一次，是两端唯一的分类来源）、NPC 价、最低价、建议卖价
  （深度感知）、P5、P10、在售量、挂单数、卖家数、卖家是否可见、竞价单数、最高竞价、
  top-8 盘口阶梯、到期桶（soon/mid/late）、推断消失量区间
  （`inferredSoldLow`/`inferredSoldHigh`）、供给增速。
  下沿是“离开某卖家”的数量（成交+撤单，排除换价），上沿是“离开某价位”的数量
  （还包含换价重挂）；卖家不可见时下沿为 0。
  只有竞价、没有一口价的条目 `minPrice = 0`，作为纯需求行导入：价格列全部为 0，
  仅 `bidOnly` / `highestBid` 有意义。

### 2.2 `WoWderhoiAH_Series`（v4）

按 `realm|faction` 键控的分层序列。每个物品存并行数组：

```text
t, min, sell, q, e
```

序列只保留图表与卖价中位实际读取的数组。P10、挂单数、卖家数和推断消失量保存在最新快照
`WoWderhoiAH_ScanData.items` 里，由终端逐次扫描导入数据库；把它们再复制进每条历史点
只会放大 SavedVariables，没有消费方。

`e` 标记事件点（建议卖价变动 ≥10% 或供给变动 ≥25%）。保留策略：最近 24 小时全量、
24 小时–7 天每小时最后一个点、7–30 天每天最后一个点；全局 6 万点上限，按物品数量
均摊裁剪。旧管线数据在第一次 v4 扫描时丢弃，不重新解释。

### 2.3 `WoWDerhoiAH_Capture`

上一次扫描的身份表，按卖家分层：`owner（隐藏时为 ""）-> unitPrice -> { q = 数量, t = 最短剩余时间 }`。
按卖家分组而不是拼接 `owner|price` 字符串，是因为扫描每行都要写这张表——拼字符串
意味着每条挂单一次浮点转字符串和一次长键哈希。`shape = "owner-price"` 标记新结构；
旧结构的身份表无法匹配，第一次扫描直接从空基线开始，不崩溃。

相邻扫描据此给出消失量区间：

- 下沿：离开某卖家的数量。换价不会改变卖家总量，所以被排除；撤单仍计入。
- 上沿：离开某价位的数量，包含换价重挂。
- 上一轮剩余时间不大于扫描间隔 + 60 秒的挂单视为自然到期，不计入。

卖家不可见时下沿为 0，核心退回阶段先验。结果永远标“推断”，不进入硬性利润门槛。

### 2.4 `WoWderhoiAH_Journal` 与 `WoWderhoiAH_Ledger`

Journal 是追加式事实，按 `realm|faction|character` 分册，事件种类：
`buy / post / cancel / sold / confirm / expire / craft / vendor / de / prospect / mill`。
当前插件自动写入买、挂、撤、成交（邮箱确认或挂单消失推断）、流拍与制造；
`vendor / de / prospect / mill` 已有解析与重放路径，但采集器尚未接入，导入端和界面
不假设它们一定存在。

插件在角色登录时就会建立（可能为空的）分册，因此带 Journal 的扫描总能归属到
扫描角色。终端只重放该角色的分册：角色没有事件时重放为空账本，绝不回退到同市场
其他角色的分册——那会把别人的持仓配到这次扫描的现金上。账本因此跟随最近一次
扫描的角色，游戏内每个角色看到的则是自己的账本。

Ledger 是 Journal 的纯投影：

- 买入生成批次（lot），成本按数量均摊；制造按材料逐项 FIFO 消耗，产物成本 =
  消耗材料的账面成本，采集端不报价；
- 卖出按 FIFO 消耗批次，已实现 = 收入 − 手续费 − 消耗成本；
- 商品挂单可以部分成交：成交后剩余数量继续留在在售里，卖光才退还押金；
- 上架不消耗库存，押金进入 escrow；
- 成交/撤单退还押金；流拍损失押金，货物退回；押金不重复扣；
- 分解/勘探/研磨把输入成本按产出数量分摊到产出批次；
- 账本缺失历史时记 `short_position`，不伪造成本；
- 消失且无流拍事件的在售挂单记为“推断成交”，照常标注；终端的已实现、胜率、
  Alpha 衰减与决策校准只使用确认成交，推断部分单列显示；
- 邮箱确认的成交如果对应一笔已推断的成交，写 `confirm` 原地升级该笔交易
  （补上真实手续费、清掉推断标记），而不是再记一次成交——否则同一笔钱会被
  记两遍，成本批次也会被消耗两遍。

桌面的 `src/lib/journal.ts` 用同一套规则重放，并有与 Lua 的 parity 测试。

### 2.5 邮箱成交采集

客户端只在邮箱里报告拍卖成交。`Mail.lua` 在 `MAIL_SHOW` / `MAIL_INBOX_UPDATE` 时读取
邮件表与拍卖发票（`GetInboxInvoiceInfo` 在 1.60 exe 中存在但未收录进生成文档，
`/wahdiag mail` 会打印原始字段供实测），把成交翻译成 `sold` 事件，把带附件、无钱的
退回邮件翻译成 `expire`：

- 归因顺序：附件链接 → 发票物品名/主题匹配扫描物品名 → 按总买断价唯一定位开仓挂单；
  都匹配不到就只计数、不写事件，绝不把成交记到猜测的物品上；
- 数量 = 发票总价 / 挂单单价，能识别商品的部分成交；无挂单时按 1 件记；
- `inferred = false`，事件带 `listedAt`（挂单时间）与 `censored = true`（成交在开箱时才被观测）；
- 如果这笔成交在开箱前已经被在售对账推断过，写 `confirm` 升级那笔推断，不重复记账；
- 去重指纹存 `WoWderhoiAH_MailSeen`（上限 500），重复开箱不会重复记账；
- `/wahcapture mail off` 关闭采集，系统退回推断成交；`/wahcapture mail on` 恢复。
  `/wahdiag` 会打印两个采集开关的当前状态，关闭后已入账的记录保留不动。

同一物品多次成交的暴露时间按每笔挂单分别累计，而不是首末成交时间差：后者会把
“几笔挂单同时卖出”当成极短曝光，系统性高估成交速度。

### 2.6 SQLite / Prisma

- `Market`：realm+faction，最近一次扫描的现金与角色（`character`，仅扫描的导入不改写角色），
  以及可空的开服时刻 `openedAt`（`/wahopen` 写入；`/wahopen auto` 会清空它，
  下一次扫描把这个清空同步到终端，而不是让终端继续沿用旧锚点）。持仓、成交和现金都来自同一个角色的
  一次扫描，界面显示该角色名。
- `AuctionSnapshot`：v4 全字段 + `topTiers` / `expiring`；`marketType` 保存扫描时的
  市场类型，空值只出现在该列引入前导入的旧行，核心会退回自己的分类逻辑。`priced = false`
  标记纯需求行，所有价格序列查询都必须过滤 `priced: true`。市场身份只存在 `Market` 行，
  快照不重复存 realm/faction。快照、日线与决策的 `marketId` 都是必填：它们不可能脱离
  某个市场存在，空值只会让两个市场的数据混在一起。
- `Position` / `Trade`：每次导入从 Journal 重建，整体替换，幂等。`Trade.listedAt` 保存
  挂单时间（可空），成交时间是观测时间，二者之差就是成交等待。
- `Decision`：每次扫描代际写入一次，记录阶段、行动类型、物品、理由与时间；复盘页按它
  匹配成交，用于描述性校准。
- `Recipe`：`data/recipes.forever.json` 的投影，导入时整体替换。
- `Event`：团本重置、暗月、阶段开放等需求脉冲的日历（当前只做展示，尚未接入排序权重）。

## 3. 算法

信号层把最近一次扫描代际当作“当前簿”：只有在该次扫描中仍有正价挂单的物品
（`stale = false`）会进入共享核心、行动清单与预警；未出现在该代际的物品仍保留在
`signals` 里供市场表和物品页查看，并标为“已下架”，价格是上次有货时的值。游戏内雷达
只评估当前扫描，终端因此与它描述同一本书——不会拿一件早已卖光的物品的历史报价去推荐买入。

### 3.1 三个价格

- `minP`：当前可买最低单价。
- `sellP`：深度感知卖价前沿。先算数量加权中位，剔除高于中位 3 倍的噪声挂单；
  再取累计数量达到 `q* = max(1, ceil(0.03Q), qmin)` 的最低价位。商品按数量累计，
  物品拍卖按笔数取第 `min(3, N)` 便宜的一口价。点火期 `qmin=1`，之后为 3。
- `listP = max(vendorP + 1, sellP - 1)`。

### 3.2 阶梯成本与可执行数量

```text
C(n) = Σ_j min(remaining, q_j) · p_j
pCap = listP · (1 − fee) − minUnitProfit
Qexec = min(供给(p ≤ pCap), floor(预算 / 均价), 背包容量)
```

雷达展示 `Qexec` 对应的总净利，而不是“最低价那一件”的单价利润。

预算本身以最近扫描的现金为上限：`effectiveBudget = min(规划预算, 扫描现金)`，扫描现金
未知（0）时才完全使用规划预算。终端还把这个上限用于凯利仓位，所以“可执行机会”和
“仓位建议”不会引用两笔不同的本金。

### 3.3 手续费、押金与保本

```text
售出净利 = listP · qty · (1 − fee) − 成本
售出保本 = 单位成本 / (1 − fee)
流拍保本 = (成本 + 押金) / (qty · (1 − fee))
流拍最坏损失 = 押金 + max(0, 成本 − NPC 保底残值)
```

流拍后货物退回，所以损失是押金加上“成本高于 NPC 保底价”的差额，不是整批成本。

押金成交退还，只有流拍/撤单才损失。手续费默认 5%，可通过规则源修改；中立拍卖行
15% 尚未单独建模。

### 3.4 成交概率

```text
P(fill ≤ T) = 1 − exp(−h · T)
```

`h` 按证据等级选择，输出同时带 `fillBasis`：

| 等级 | 条件 | `h` | 含义 |
|---|---|---|---|
| `own` | 自己的成交 ≥ 3 笔 | `ownSold / ownExposedHours / qty` | 唯一干净标签；暴露时间按每笔挂单累计 |
| `proxy` | 有公共推断消失 | `inferredSoldLow / (supply · elapsed)` | 用区间下沿；上沿含换价重挂，不能当成交 |
| `prior` | 都没有 | 阶段 × 市场类型基线 | 开服冷启动的结构先验 |

样本少于 3 时自己的成交不算证据；三种等级都输出 `[low, high]` 区间，界面标注来源。
`own` 来自 Journal 的 `sold` 事件（近 7 天，`inferred = false`，只算拍卖行渠道）。曝光
小时是每笔成交各自 `max(观测时间 − 挂单时间, 扫描间隔)` 之和，不是首末成交的跨度：
几笔挂单在同一小时内卖出时，后者会把曝光压到一个扫描间隔，直接放大成交率。桌面端
从 `Trade` 表用完全相同的过滤条件与公式重建，游戏内与终端输入同一形状。

核心同时返回 `h` 本身（`fillHazard`），图表的价格—成交曲线直接以它为锚，不再从
`fillProb` 反推：在长窗口下 `h` 被上限截断时，`fillProb` 会舍入成 1，反推会得到
“没有估计”。曲线越往高价、前方供给越多，成交概率越低；区间带取自核心的
`fillProbLow/fillProbHigh`，不是图表自己的常数。

### 3.5 阶段

```text
phase = ignition  if age < 6h  or breadth < 80
        wave      if age < 48h or breadth < 400
        settle    if age < 168h or breadth < 800
        steady    otherwise
```

`breadth` 是最近一次扫描中有正价的物品种类数：已下架物品保留历史，但不再计入市场宽度。
`/wahphase` 可手动覆盖；桌面用 `AQT_PHASE` 覆盖。桌面在每次请求时按“库里最早扫描时间 +
当前代际的 breadth”重算阶段，再作为 `phaseOverride` 传给共享核心；阶段跨越边界会触发
市场重建，所以即使扫描暂停，阶段也会像游戏内的 `WAH.currentPhase` 一样随真实时间推进。
核心不会用单次快照窗口重新推算阶段，否则活跃市场会因为“最近一次扫描是几分钟前”而被
永久判成点火期。阶段决定历史窗口、样本门槛、价差窗口与净利门槛：

| 类型 | 点火期 | 洪流期 | 沉淀期 | 稳态 |
|---|---|---|---|---|
| vendor | NPC 必买，不经门槛 | 同左 | 同左 | 同左 |
| commodity 价差 | 20–85% | 12–60% | 8–50% | 6–40% |
| item 价差 | 25–80% | 18–70% | 15–60% | 12–50% |
| commodity 挂单/卖家 | 1/1 | 3/2 | 5/3 | 8/4 |
| item 挂单 | 1 | 2 | 3 | 3 |

净利与单价利润门槛见 `src/lib/market-rules.ts`；它是唯一事实源，编译到
`GeneratedRules.lua`，漂移测试保证两边一致。

### 3.6 排序

- 点火期：NPC 套利 > 净利 × 成交率 × **需求先验**（存在竞价时先验 ×1.2）；
- 洪流期：净利 × 成交率 / max(供给增速, 0.1)；
- 沉淀/稳态：净利 × 成交率 × 置信度。

竞价是客户端唯一直接暴露的需求信号：`highestBid > 0` 只在点火期抬高排序权重，
不放松任何门槛，也不进入置信度。之后按排序做一次共享预算分配（见 3.8）。

需求先验来自 `src/data/demand-bands.json`：背包、魔杖、药水、食物、弹药、附魔材料在
开服前段权重更高；护甲等分散需求权重更低；未匹配为 1.0。同一张表编译到
`GeneratedRules.lua` 的 `WAH.DEMAND`，游戏内与终端共用。它只在点火期参与排序，
有了自己的成交后由成交率接管。

NPC 套利永远第一：它没有市场风险，只有预算和背包约束。

### 3.7 生产网络

```text
max_x (pᵀA − cᵀ) x   s.t. Bx ≤ b, x ≥ 0
```

- 变量：每条配方的制造次数；
- 目标：成品建议卖价 × 数量 × (1 − 手续费) − 材料成本；
- 约束：每专业每日制造次数、材料在售量、预算；
- 对偶变量：影子价格——多一个产能单位值多少金币；
- 小规模稠密单纯形；候选先按单件净利截断到 120 条；LP 解向下取整，净利按整数
  计划重算；求解失败时回退到贪心并在界面标注。

配方数据来自「无限图鉴 wuxianwow.com」的 1.60 客户端导出，共 2,595 条（1,147 条
1.60 新增），含权威材料与产物 itemId。产能是终端配置，不是客户端事实。

游戏内另有一份只含材料的编译表 `GeneratedRecipes.lua`（`npm run recipes:lua` 生成，
约 154 KB）：`Craft.lua` 监听 `TRADE_SKILL_CRAFT_BEGIN` 与
`TRADE_SKILL_ITEM_CRAFTED_RESULT`，把制造写成带产物、数量与 `mats` 的 `craft` 事件。
配方 id 先按 spell id 查，再按 `C_TradeSkillUI.GetRecipeInfo().recipeID` 查，最后按
“唯一产物”回退；都不中记 `craft_unmapped`，不写账本——宁可少记，不可把成本记到错配方上。

### 3.8 组合与仓位

```text
f* = p − (1 − p) / b,  b = 盈利 / 亏损
仓位 = kappa · f*，再受单物品敞口与日预算约束
```

亏损 = 单位成本 − 残值（NPC 价/分解价），所以有保底的物品是更小的赌注。样本不足
时标 `exploratory`，不把先验成交率当成估计出来的概率。

分配在共享核心的 `Core.allocate` 里完成，游戏内与终端跑同一份：按已排好的行依次分配，
`remaining = min(预算, 现金) × dailyBudget`，每行 `allocQty = min(盘口深度, Kelly 预算,
剩余预算 / 单价)`，只减不增。雷达的数量列、净利列和终端行动清单都使用 `allocQty`，
`execQty` 只表示盘口深度；同一行的数量与利润必须描述同一笔交易。

### 3.9 学习与校准

- **离策略评估**：把决策与后续成交按物品和时间窗口匹配，按倾向加权，报告覆盖率与
  有效样本量。倾向为 1 时它退化为描述性匹配，界面明确说明“不是因果效应”。
- **Alpha 衰减**：按周分桶的胜率与确认成交的已实现 P&L；推断成交单列展示，不进入
  校准。最近窗口胜率下降 15 个百分点，或连续两个正窗口后转负，触发提示。
- **受控实验**：围绕建议卖价设计 2–5 个价位的小批量挂单；复盘页按物品 + 价位把确认
  成交与 `listedAt` 配对，报告成交笔数、件数与中位成交时长。未成交挂单没有持久化，
  所以不计算成交率——没有成交就显示“未成交”，不显示 0%；
  结论只用于调整下一轮价位，不直接改全局阈值。

### 3.10 宏观 deflate

```text
p_real(t) = p(t) / P(t) · 100
```

`P(t)` 是每日全市场物品建议卖价的中位，归一化到第一个有数据的日子。缺失日沿用上一
个观测值，不插值。跨天比较用真实价格；同一天内用名义价格。

## 4. 单一决策核心

`addon/WoWderhoiAH/Core.lua` 是唯一实现：

- 无 WoW API，Lua 5.1 兼容，输入输出都是普通表；
- 游戏内由 `WAH.coreInput()` 组装输入；
- 桌面由 `src/lib/core/from-market.ts` 用同一形状组装，经 fengari 运行；
- `addon/test/core-parity.test.ts` 对比两条加载路径的输出。

`Trade.lua`、`Sell.lua` 和终端页面都只渲染 Core 的输出，不重新实现定价或排序。

## 5. 运行边界

- 客户端没有成交历史接口；公共成交不可观测。
- `GetBids` / `QueryBids` 只覆盖玩家自己的竞价，不是全市场买单。
- `GetReplicateItemTimeLeft` 可能返回秒或档位；`/wahdiag` 实测并降级。
- `PostItem` / `PostCommodity` / `CancelAuction` 带 `HasRestrictions`；被拦截时
  降级为手动价格助手，不重试、不假装成功。
- 插件不做全自动扫货或上架；每次购买与上架都经过客户端确认。
- 公共捡漏/低吸/高抛视图已经商品化；优势来自执行、私有成交、产能与资本配置。

## 6. 验收清单

1. 第一次扫描写入 v4：盘口、卖家、到期桶、竞价、扫描龄、可选开服时刻。
2. 买 → 挂 → 成交/流拍闭环可重放，P&L 与金币变化一致（误差 = 手续费 + 押金）。
3. 邮箱成交写入 `inferred = false` 的 `sold`；若该笔此前已被推断，则写 `confirm` 升级，
   同一笔成交只记一次账；重复开箱不重复记账；成交率按暴露时间估计。
4. 制造写入 `craft`，产物成本等于材料 FIFO 账面成本；材料未入账时标短头寸，不静默记零。
5. 雷达每行有可买数量（分配后）、买价、建议卖价、净利（分配后）、成交率。
6. 所有百分比带分母与窗口；P10 只出现在统计区。
7. 图表 0/1/2 点时显示盘口，不显示空框。
8. 卖出页算押金、售出/流拍保本价，被拦截时降级。
9. 同一扫描，Lua 与 fengari 输出一致；预算内分配与终端行动清单数量一致。
10. 背包空位来自客户端；`/wahopen` 后阶段按开服时刻推进。
11. 配方网络可导入、可求解，影子价格可见，退化有标注。
12. 性能门禁通过；`/wahdiag` 每项都有结论。
