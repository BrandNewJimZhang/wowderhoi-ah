# 游戏内功能设计评审

> 对象：`forever` 分支（魔兽世界：无限 1.60.1，Interface 16001）
> 结论时间：2026-11-05
> 结论：数据采集与“捡漏”已经能跑通，但**交易决策、卖出闭环、数据可信度**三块仍是半成品。当前产品更像“扫描器 + 折扣列表”，还不是“交易工具”。

## 本次已经落地的部分

这次适配先把“能在无限服上跑”做完了：

- 扫描器改走 `C_AuctionHouse.ReplicateItems()`，不再依赖旧版
  `QueryAuctionItems`/`GetAuctionItemInfo`；修掉了每 200 行跳一条的
  off-by-one，并加了超时与“物品搜索误触发旧复制结果”的保护。
- WAH 交易页改为独立面板，不再注入 `AuctionFrame` 标签；物品拍卖按
  auctionID 核价购买，商品按数量走客户端确认框。
- `/wahprice` 取代了无法移植的卖单预填。
- Lua 测试桩改为模拟无限客户端，覆盖复制扫描、商品阶梯计价、
  价格变化中止、价格指引等路径。

下面分析的是**还没做**的部分，按优先级排序。

## 0. 一句话结论

雷达回答的是“哪个挂单比参考价便宜”，而玩家真正要回答的是：
**“现在买多少、花多少、多久能卖出去、扣掉手续费还剩多少、卖不出去怎么办。”**
后四个问题目前插件一个都没有回答。

## 1. 现状盘点

| 能力 | 现状 | 主要缺口 |
|---|---|---|
| 全量扫描 | `C_AuctionHouse.ReplicateItems()`，8ms/帧分片处理 | 无自适应频率、无增量、扫描会让玩家自己的浏览结果被覆盖 |
| 价格统计 | 量加权 min/P5/P10 + 深度感知卖价前沿 | 只有挂单，没有成交；P10 的适用性按市场类型未区分 |
| 历史 | `WoWDerhoiAH_Points`，7 天窗口、每物品最多 192 点 | 192 点在 15 分钟节奏下只有约 48 小时，和“7 日”口径矛盾 |
| 捡漏雷达 | NPC 必赚 + P10 中位折扣，三道闸门 | 利润按单价算，没有可执行数量、手续费、资金/背包约束 |
| 购买 | 物品按 auctionID 核价后一口价；商品按数量市价买 | 商品实际成交价可能跨档；无批量、无预算、无背包检查 |
| 卖出 | `/wahprice` 打印建议卖价 | 不能上架、不算押金、不监控压价、不重挂 |
| 提示框/图表 | tooltip 价格块 + 3h/48h 折线 | 信息层级偏多，缺少“买/卖/风险”的语义分组 |
| 设置/入口 | 插件列表按钮、`/wahscan`、`/wahauto`、`/wahtrade`、`/wahprice` | 无首次引导、无关键绑定、无游戏内状态面板 |
| 数据管道 | SavedVariables → watcher → 终端 | 必须小退/`/reload`；终端预警/关注列表不能回写游戏 |

## 2. 根因分析

### 2.1 “挂单”被当成了“成交”

所有统计量都来自当前挂单：

- 7 日 P10 中位是**挂单价的分布**，不是成交价。
- `minMed7Distinct`、`maxDiscount` 是在用代理指标猜“这个参考价是否可信”。
- 没有成交量、成交速度、成交价，无法回答“这个价能不能卖掉”。

无限服的拍卖行接口不提供历史成交，这是客户端事实，不是实现偷懒。因此方向不是“找到成交数据”，而是**把挂单数据能支持的结论和不能支持的结论分开**：

- 能支持：当前最低可买价、深度、供给、挂单价的分位结构、NPC 保底。
- 不能支持：真实成交价、成交速度、某价位能否卖出。
- 需要新增的代理：挂单消失速度（两次扫描之间消失且未到期的挂单）、同物品重复上架频率、卖价前沿的移动速度。这些都能从连续扫描推导出来，但当前一条都没存。

### 2.2 利润模型缺少“可执行数量”

当前雷达：

```text
profit = med7 - minPrice
```

这是“买一件能赚多少”的单价利润。实际交易里：

- 最低价可能只有 1 件，买完就没了。
- 参考价可能对应的是没人接盘的挂单，卖不出去。
- 5% 拍卖行手续费、押金、重挂成本都没扣。
- 背包、资金、来回拍卖行的时间都是约束。

**目标形态：**

```text
executable = min(价格 ≤ 阈值的挂单数量, 预算 / 单价, 背包空位)
expectedProfit = (reference - price) * executable - fees
risk = vendor | commodity | item
confidence = f(历史样本数, distinct, 扫描覆盖时长, 深度)
```

雷达应展示 `可买数量 / 预计利润 / 风险等级 / 置信度`，而不是只展示折扣百分比。

### 2.3 商品与物品拍卖是两套交易语义

无限服（现代客户端）把拍卖行拆成：

- **商品（commodity）**：可堆叠材料，匿名报价组，按数量成交，成交价取最低档位，可能跨多个价位。
- **物品拍卖（item auction）**：唯一拍卖，有 auctionID、一口价/竞价，按整笔成交。

当前 UI 用同一张四列表和同一个“购买”按钮覆盖两者，只靠 `Buy*` 标签区分，这是不够的：

- 商品点击某一行的“购买*”，实际买到的是**当前全市场最低价**，不一定是你点的那一行。
- 商品总价可能跨档，行上的“总价”只是该档位的估算，不是最终成交价。
- 物品拍卖的竞价单（无一口价）被直接过滤，用户看不到“有货但只能竞拍”。

**目标形态：**

- 商品行显示“市场价 + 可买数量 + 预计总价区间”，购买前弹出成本预览。
- 物品行显示“一口价 / 竞价”两种动作，竞价单单独标记。
- `Buy*` 这种脚注式标签应被真正的“市场购买”动作取代。

### 2.4 数据口径与历史窗口自相矛盾

`WoWderhoiAH_Points` 的注释写“7 天窗口，每物品最多 192 点（15 分钟一次约 48 小时）”。这两句话不能同时成立：

- 15 分钟一次 × 7 天 = 672 点。
- 192 点上限会把窗口截断到约 48 小时。
- 于是“7 日 P10 中位”实际是“最近 48 小时、最多 192 个样本的中位”。

在 TBC 周年服上，这个偏差被“扫描次数少、样本本来就少”掩盖了；到无限服，15 分钟自动扫描 + 9000+ 挂单会让它变成一个明确的错误标签。

**修复方向（二选一，不要继续含糊）：**

1. 把口径改成“48 小时 P10 中位”，所有 UI/终端/文档统一改词；或
2. 保留 7 天，但历史改为**分层采样**：最近 48 小时保留每次扫描，48 小时以前每小时保留一个收盘点，上限提高到约 400 点。

推荐 2：7 天窗口对“周末/重置日”这类周期性判断有价值，且分层采样不会让 SavedVariables 线性膨胀。

### 2.5 无限服的经济结构与 TBC 不同，规则不能直接照搬

无限服的拍卖行体量（参考「无限图鉴」2026-10-26 采集：9424 条挂单、866 种在售物品）远大于 TBC 周年服的薄订单簿。当前规则是在“上层挂单又薄又陈”的前提下调的：

- `minAuctions = 3`：在无限服的商品市场太低，3 个挂单可能只是同一个卖家的分堆。
- `minProfit = 500`（5 银）：无限服正常物价以金计，5 银门槛几乎不筛任何东西。
- `discount = 0.85`：商品市场价差通常很窄，15% 折扣很少见；物品拍卖（幻化、稀有）价差可以很大，15% 又太松。
- `maxDiscount = 0.6`：对幻化/收藏品，90% 低于一个陈旧参考价可能是正常的，不一定是参考价坏了。

**目标形态：** 规则按市场类型分组，而不是全局一套：

```text
vendor:    无历史门槛，无利润门槛（现状正确）
commodity: 高流动性门槛（挂单数/卖家数）、低折扣门槛、按数量加权
item:      低流动性门槛、高折扣上限、要求更长历史和更多 distinct
```

### 2.6 账户级 SavedVariables 混用了服务器/阵营/角色

`WoWderhoiAH_ScanData` 记录了 `server` 和 `faction`，但历史 `WoWDerhoiAH_Points` 只按 `itemId` 存。一个账号在联盟/部落、不同服务器、不同角色上扫描时：

- 上一次扫描的 `items` 会被直接覆盖（这个是有意的“当前市场快照”）。
- 历史点会把不同阵营/服务器的价格混进同一条曲线。
- 雷达的 med7 因此可能引用另一个阵营的价格。

**修复方向：** 历史键改为 `server .. "|" .. faction .. "|" .. itemId`，或在切换服务器/阵营时清空历史并明确提示。前者更稳，后者更简单；至少要在写入点做一次一致性检查。

### 2.7 全量复制会覆盖玩家自己的浏览结果

`ReplicateItems()` 会把整个拍卖行的结果写进客户端的浏览结果缓存。玩家正在拍卖行里搜索某件物品时，插件的自动扫描可能把结果替换掉。当前实现没有任何避让：

- 自动扫描每 15 分钟触发一次，不管玩家是否正在浏览。
- 玩家自己的搜索和插件的 `SendSearchQuery` 共用同一套结果缓存。

**修复方向：**

- 自动扫描只在玩家打开 AH 后的前 N 秒、或玩家 5 分钟无操作时触发。
- 玩家发起搜索时暂停自动扫描（`lastPlayerActionAt`）。
- 扫描完成后如果玩家有未完成的搜索，恢复它。

### 2.8 卖出闭环完全缺失

现代客户端没有插件可读的“出售槽”接口，所以旧版的“预填一口价”无法移植。这不是可以绕过的实现细节，而是必须重新设计的产品能力：

- `/wahprice` 只解决了“卖多少钱”，没解决“怎么挂、挂多少、押金多少、卖不掉怎么办”。
- 没有押金计算：`C_AuctionHouse.CalculateItemDeposit` / `CalculateCommodityDeposit` 都是可用的。
- 没有 5% 手续费的盈亏平衡价。
- 没有“我的在售”列表、到期重挂、被压价提醒。
- 没有成交记录（`OWNED_AUCTIONS_UPDATED`、邮件、`AUCTION_HOUSE_AUCTION_CREATED` 等信号可用）。

**目标形态：** `/wahsell` 或交易页的“卖出”模式：

```text
选择背包物品 → 显示建议价、押金、手续费、盈亏平衡价
→ 选择数量/堆数 → 调用 PostItem/PostCommodity → 客户端确认
→ 记录本次上架 → 轮询 OwnedAuctions 做到期/被压价提醒
```

### 2.9 购买流程的校验不完整

- 物品拍卖只校验 `buyoutAmount`，没校验 `quantity` 和 itemKey；同一 auctionID 的整笔拍卖理论上不会变，但接口返回值应全部核对。
- 商品只校验第 1 档的 `unitPrice`，实际成交会跨档；提示文案里的“约 X”必须明确是估算，最终以客户端确认框为准（当前已这样写，但行上的“总价”仍会被误读）。
- 没有背包空位检查，买完发现装不下。
- 没有购买后的成交记录，无法复盘“这笔到底赚没赚”。

### 2.10 名称搜索的解析不够稳

现代 API 是 itemKey 驱动的，没有“按名字模糊搜索整个拍卖行”的等价接口。当前实现：

1. 先在本次扫描的物品名里找精确/前缀/子串匹配；
2. 找不到再 `SendBrowseQuery`，取返回的第一个 itemKey。

问题：

- 中文名、英文名、别名、带后缀的物品可能匹配到错误条目。
- “第一个结果”不一定是玩家想要的那个。
- 扫描数据缺失时（新物品、未扫描），体验会突然降级。

**目标形态：** 搜索结果先展示一个**物品选择列表**（browse results 本身就是按物品聚合的），玩家点选后再进入报价簿；雷达行直接带 itemId，跳过解析。

### 2.11 错误与状态反馈只有聊天框

扫描超时、节流、AH 关闭、搜索结果为空、价格变化，全部通过 `DEFAULT_CHAT_FRAME` 播报。聊天框会被其他插件刷走，玩家在交易页上看不到“当前为什么是空的”。

**目标形态：** 交易页内固定状态行（`trade.status`），显示：

- 上次扫描时间 / 数据版本 / 物品数
- 当前搜索状态（解析中 / 结果数 / 失败原因）
- 购买结果（成功 / 变价 / 确认中）

聊天框只保留需要离开页面后仍可见的信息（扫描完成、需要 `/reload`）。

### 2.12 性能与持久化预算缺失

- 无限服一次复制约 9000+ 条挂单；8ms/帧、200 条/帧，约 45 帧完成，这个设计是合理的，但没有性能门禁。
- SavedVariables 落盘体积没有预算：866 种物品 × 192 点 ≈ 16.6 万点，加上每次扫描的完整 `items` 表，退出游戏时的序列化可能明显卡顿。
- 没有“扫描期间关闭 AH”“扫描被节流”的压测用例。

**建议：** 在 `scripts/perf/` 增加一个纯 Lua/Node 的合成数据门禁：生成 1000 种物品 × 192 点，断言 `finishScan` 的处理时间和序列化后大小上限。

## 3. 优先级路线图

### P0 — 让“结论”可信（1–2 周）

1. **统一历史口径**：7 天分层采样，或明确改成 48 小时；同步改所有 UI/终端/文档文案。
2. **历史按 server+faction 键控**，或在切换时清空并提示。
3. **交易决策模型**：利润按可执行数量 ×（参考价 − 买价 − 手续费）计算，新增押金/手续费字段。
4. **商品成本预览**：购买前显示“预计跨档成本区间”，明确最终以确认框为准。
5. **补全购买校验**：quantity、itemKey、背包空位。
6. **状态行**：交易页内显示扫描/搜索/购买状态，不再只靠聊天。

### P1 — 补全交易闭环（2–4 周）

7. **卖出模式**：选物品 → 建议价 + 押金 + 盈亏平衡价 → PostItem/PostCommodity → 记录上架。
8. **在售管理**：到期、被压价、成交提醒；一键重挂。
9. **物品选择列表**：browse results 作为搜索结果的第一层，点选进入报价簿。
10. **批量购买**：按预算/数量/利润阈值一次买多笔；商品按目标数量购买。
11. **规则分组**：vendor / commodity / item 三套阈值；终端与插件共享同一份规则源。
12. **自适应扫描频率**：玩家操作时暂停；AH 打开后按市场活跃度调整。

### P2 — 长期能力（4 周以上）

13. **挂单消失速度**：从相邻扫描推导“近似成交量/成交速度”，作为置信度输入。
14. **跨角色/跨阵营合并**：账号级市场视图，但历史按市场隔离。
15. **终端回写**：关注列表、预警阈值同步到游戏内。
16. **无限服配方表**：用「无限图鉴」的配方数据替换当前 TBC 配方表；制造成本纳入雷达。
17. **性能门禁**：复制扫描处理时间、SavedVariables 体积、搜索响应时间。

## 4. 建议的目标数据模型

```lua
-- 一次扫描的每个物品条目
{
  itemId, name, quality, itemClass, itemSubClass,
  minPrice, sellP, p5, marketPrice,
  quantity, numAuctions,
  vendorP,
  -- 新增
  sellerCount,          -- 不同卖家数（replicate 的 owner 字段可以聚合）
  executableQuantity,   -- 当前价位的可买数量
  deposit,              -- 按建议卖价计算的押金
  feeRate,              -- 拍卖行手续费
  confidence            -- 0..1，由历史样本/覆盖时长/distinct 推导
}

-- 历史点
{ t = epoch, c = P10, q = listedQuantity, n = numAuctions, s = sellerCount }
```

## 5. 无限服适配中已经确认的客户端事实

以下来自「无限图鉴 wuxianwow.com」的 1.60.1.70634 插件 API 文档，作为实现依据：

- 现代 `C_AuctionHouse`：`ReplicateItems`、`SendSearchQuery`、`GetItemSearchResultInfo`、`GetCommoditySearchResultInfo`、`PlaceBid`、`StartCommoditiesPurchase`、`PostItem`、`PostCommodity`、`CalculateItemDeposit`、`CalculateCommodityDeposit`。
- `ItemKeyInfo.isCommodity` 区分商品与物品拍卖。
- `GetReplicateItemInfo` 只给 `itemID`，不给后缀/等级；按 itemID 聚合是接口层面的限制。
- 旧版 `QueryAuctionItems`、`GetAuctionItemInfo`、`CanSendAuctionQuery`、`PlaceAuctionBid`、`GetAuctionSellItemInfo`、`MoneyInputFrame_SetCopper` 均不在文档中。
- TOC 支持 `## AllowLoadGameType`（无限对应 `camelot`）、`## AddonCompartmentFunc`、`## Interface: 16001`。
- `AuctionHouseFrame` 是 Blizzard UI 的全局框架；不在 API 文档里，因此代码用事件状态（`AUCTION_HOUSE_SHOW/CLOSED`）做开关判断，不依赖框架名。

## 6. 不建议做的事

- **不要为了“完整”而伪造成交数据。** 没有成交接口就是没有；用挂单消失速度做代理时必须标成“推断”。
- **不要做全自动扫货/自动上架循环。** 购买和上架都应保持玩家一次明确的动作，客户端确认框是最后一道闸门。
- **不要把两套客户端塞进同一个分支。** 现代/旧版拍卖行 API 的差异是结构性的，双分支 + 共享核心比运行时适配更可控。
- **不要继续用 `Buy*` 这种脚注解释商品语义。** 应该让商品和物品在 UI 上就有不同的动作和成本表达。

## 7. 给下一步的实现顺序

1. 先修历史口径与 server/faction 键控（数据错了，后面全错）。
2. 再改雷达的利润模型与规则分组（决定“值不值得买”）。
3. 再做商品成本预览与购买校验（决定“买得对不对”）。
4. 然后做卖出模式与在售管理（补上闭环）。
5. 最后做物品选择列表、批量购买、终端回写（体验与规模）。
