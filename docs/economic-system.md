# 地精经济系统：设计与算法

本文是 `forever` 分支的实现说明。它回答三个问题：系统把什么当作事实、如何从事实得到行动、哪些结论不能从客户端数据里得到。

## 1. 本体与十条不变量

系统的主语不是“物品价格”，而是**玩家的经济行动**。数据流分成六层，层与层之间的时钟不同：

```text
公共行情（拉取）   -> MarketGeneration   不可变观测，按扫描代际
私有资产（推送）   -> Estate             按角色/账号；carried/bank/mail/listed；带 coverage
动作事实（追加）   -> JournalFact + LedgerCheckpoint   稳定序号，永不删除已入账事实
对账               -> Holding            数量、位置、已知/未知成本、差额
计划               -> Plan               版本化、资源可行、买卖统一排序
学习               -> Decision           不可变，绑定 plan revision
```

市场盘口必须主动 `ReplicateItems` 才能拿到，只能按扫描代际更新；背包、银行、邮件、自有挂单和现金是客户端本地事件，必须实时推送。把两类数据塞进同一个扫描快照，会让终端在两次扫描之间用冻结的现金、空位和事件投影去回答“现在该做什么”。

十条不变量：

1. 决策单位是头寸/行动/论点，不是雷达行。
2. 目标函数显式：风险调整后的真实金币/真实分钟，受资金、背包、冷却、注意力约束。
3. 需求标签来自自己的成交/竞价/实验；公共消失只是区间先验。
4. 生产网络 = 配方图 + 容量约束 + 影子价格。
5. 竞争 = 对手图 + 市场影响 + 反射性。
6. 信念状态带不确定性，并主动设计实验。
7. 执行 = 游戏内驾驶舱 + 条件策略 + 人工确认。
8. 决策核心只有一份，游戏内与桌面共用 `Core.lua`。
9. 名义价格 deflate 到真实/相对价格。
10. 运行可靠性：数据新鲜、失败降级、扫描不丢。

在此之上，状态与计划必须满足七条结构不变量：

1. **未观测 ≠ 零**：银行没打开、邮箱没开、在售没查询，状态是 `unobserved`，不是空集合。
2. **状态不写回观测**：新状态产生新计划版本，旧代际与旧决策不被改写。
3. **事实只追加**：终端不因一次导入删除历史成交与成本；本地日志截断由检查点承接。
4. **对账显式**：\(\text{ledgerQty} + \text{unknownQty} = \text{carried} + \text{bank} + \text{mail} + \text{listed}\)；差额是界面状态，不是静默截断。
5. **计划必须可执行**：任一步骤消耗的现金与空位，不得超过执行到该步时的可用量；卖出回款和释放的空位进入后续买入预算。
6. **计划全序且与成本无关**：买卖用同一货币（金币/分钟）排序，`itemId` 兜底；历史成本只用于 `realizedPnl` 报告，不进入排序。
7. **决策不可变**：同一个 `decisionId` 永远对应同一份预测；采纳事件引用确切的 `planRevision`。

## 2. 数据契约

桌面端的每一次读取都按 `Market`（realm + faction）隔离：默认取最新扫描所属市场，
可用 `AQT_MARKET="realm|faction"` 固定。行情代际、序列、头寸、成交、决策都不会跨市场合并。

### 2.1 `WoWderhoiAH_ScanData`（v4）

一次全量扫描的最新快照：

- 元数据：`dataVersion`、`observationVersion`（观测洁净度：2 表示推断消失量已剔除
  自有挂单与自有买入）、`scannedAt`、`server`、`faction`、`character`、`cash`、
  `bagSlots`（扫描时的背包空位；终端的权威是 Estate 的实时 `freeSlots`，这个字段只作为尚未推送 estate 时的播种值）、`total`。
- `items[itemId]`：名称、品质、物品类别、市场类型（`marketType`：`commodity` | `item`，
  扫描时按当时的物品记录判定一次，是两端唯一的分类来源）、NPC 价、最低价、建议卖价
  （深度感知）、P5、P10、在售量、挂单数、卖家数、卖家是否可见、`ownerVisible`、
  `selfExclusion`（`owner` / `owned` / `none`，即自有挂单的识别通道）、被排除的自有
  挂单数与件数（`selfListings`/`selfQty`）、卖家集中度（`sellerHHI`、`topSellerShare`）、
  竞价单数、最高竞价、top-8 盘口阶梯与 `tierTruncated`（阶梯不止八档时为 true，
  核心据此把不可见深度计入队列）、到期桶（soon/mid/late）、推断消失量区间
  （`inferredSoldLow`/`inferredSoldHigh`）、供给增速、扫描时按阶段窗口统计的
  `historySamples`（终端直接使用；没有该字段的旧快照回退到卖价样本数）。

  自有挂单不进入盘口、卖家数、供给与消失量：卖价前沿必须是别人的报价，否则卖出页会
  建议你压自己 1 铜，`minSellers` 也会被你自己满足。`owner` 带 `-Realm` 后缀时按 `-`
  之前比较；owner 不可见时用 `GetOwnedAuctions` 按物品、买断价、数量匹配，匹配不到标
  `none`，这一行不参与先验校准。

  推断消失量的下沿是“离开某卖家”的数量（成交+撤单，排除换价），上沿是“离开某价位”
  的数量（还包含换价重挂）；卖家不可见时下沿为 0。两个边界都会减去同一窗口内
  Journal 记录的自有买入件数：自己买走的东西是自家需求，不是市场证据。

  只有竞价、没有一口价的条目 `minPrice = 0`，作为纯需求行导入：价格列全部为 0，
  仅 `bidOnly` / `highestBid` 有意义。

### 2.2 `WoWderhoiAH_Series`（v4）

按 `realm|faction` 键控的分层序列。每个物品存并行数组：

```text
t, min, sell, q, n, e
```

序列只保留图表、回填与卖价中位实际读取的数组。P10、卖家数和推断消失量保存在最新一次扫描
`WoWderhoiAH_ScanData.items` 里，由终端逐次扫描导入数据库；把它们再复制进每条历史点
只会放大 SavedVariables，没有消费方。挂单数 `n` 随点保存，因为回填时只有它能把
“空书”和“缺测”分开；旧点没有该数组时按 0（未知）补齐，所有数组保持等长。

`e` 标记事件点（建议卖价变动 ≥10% 或供给变动 ≥25%）。保留策略：最近 24 小时全量、
24 小时–7 天每小时最后一个点、7–30 天每天最后一个点；全局 6 万点按物品数量均摊成
每物品预算（至少 8 点），超出时等距折叠并保留首点、末点与事件点，而不是从尾部截断。
旧管线数据在第一次 v4 扫描时丢弃，不重新解释。

### 2.3 `WoWderhoiAH_Capture`

上一次扫描的身份表，按卖家分层：`owner（隐藏时为 ""）-> unitPrice -> 打包数`。
打包数是一个 double：`quantity * 2^20 + 时间码`，整数部分为数量，低 20 位是最短
剩余时间（0 表示未知）。按卖家分组而不是拼接 `owner|price` 字符串，是因为扫描每行
都要写这张表——拼字符串意味着每条挂单一次浮点转字符串和一次长键哈希；每个
`(卖家, 单价)` 存一张 `{ q, t }` 小表则要在 17 万行扫描里分配同样多的表。
`shape = "owner-price-packed"` 标记该结构；旧的 `owner-price` 身份表无法匹配，
第一次扫描直接从空基线开始，不崩溃。

相邻扫描据此给出消失量区间：

- 下沿：离开某卖家的数量。换价不会改变卖家总量，所以被排除；撤单仍计入。
- 上沿：离开某价位的数量，包含换价重挂。
- 上一轮剩余时间不大于扫描间隔 + 60 秒的挂单视为自然到期，不计入。

卖家不可见时下沿为 0，核心退回阶段先验。结果永远标“推断”，不进入硬性利润门槛。

### 2.4 `WoWderhoiAH_Journal` 与 `WoWderhoiAH_Ledger`

Journal 是追加式事实，按 `realm|faction|character` 分册，事件种类：
`buy / post / cancel / sold / confirm / expire / bid / craft / vendor / de / prospect / mill /
transfer_out / transfer_in / adopt`。
每册维护单调序号 `seq`；事件同时记录 `t`（写入时刻）、
`observedAt`（插件确认该事实的时刻）与 `censored`（两者不同时为 true）。序号是终端去重的
唯一身份：同一册的 `(character, epoch, seq)` 只会写一次。分册另有内容修订
`rev`：追加事件和原地补全同一事件（例如原生事件先按估算价入账、随后拿到 UI 的
精确成本或押金）都会推进它。watcher 用它判断“事实内容变了但没有新序号”，计划
身份也把它当作账本修订。

`epoch` 是分册创建时刻。清除 SavedVariables 或重装插件会让序号从 1 重新开始，
`epoch` 让新分册的事实与旧分册分开；终端只用最新 `epoch` 的分册重放当前持仓，
旧分册保留为历史与成交事实。终端为每个 `(market, character, epoch)` 记一行
`JournalBook`，因此重置后立即建立、还没有任何事件的空分册也能成为当前账本。

当前插件自动写入买、挂、撤、成交（邮箱确认）、流拍、竞价与制造；
`vendor` 通过 `/wahcost` 手动补记（客户端没有逐笔卖店事件，只有一条本地化汇总行）；
`de / prospect / mill` 有解析与重放路径但没有干净的客户端结果事件，采集器不接，
导入端和界面也不假设它们一定存在。

“从自有挂单列表消失”不再被推断为成交。取消、到期和成交都有客户端事件或邮件；
无法归因的消失只记 `unobserved`，不记收入，也不产生已实现盈亏。

跨角色转移用 `/wahtransfer <itemId> <数量> out` 在发送角色记录 FIFO 成本，
再在接收角色用 `/wahtransfer <itemId> <数量> in <单位成本>` 记入同一成本；
只记一边比不记更糟，账本会互相矛盾，所以这条路径刻意做成手动。邮箱扫描同时统计
邮箱里未领取的金币（`Mail.pendingCash`），显示在状态行的“在途”，但**不进入预算**：
`GetMoney()` 仍是唯一可花费现金。

插件在角色登录时就会建立（可能为空的）分册，终端按
`(market, character, epoch, seq)` 逐册追加事实，并按角色重建持仓；一次扫描的
兜底计划只读扫描角色的持仓，绝不回退到同市场其他角色的分册——那会把别人的持仓
配到这次扫描的现金上。账号级在售与
账号银行只由一个角色承载（最近一次 estate 观测的角色；没有 estate 时
回退到最近扫描的角色），避免跨角色重复计数；每个角色游戏内看到的仍是自己的账本。

Ledger 是 Journal 的纯投影：

- 买入生成批次（lot），成本按数量均摊；制造按材料逐项 FIFO 消耗，产物成本 =
  消耗材料的账面成本，采集端不报价；
- 卖出按 FIFO 消耗批次，已实现 = 收入 − 手续费 − 消耗成本；
- 商品挂单可以部分成交：成交后剩余数量继续留在在售里，卖光才退还押金；
- 上架不消耗库存，押金进入 escrow；
- 成交/撤单退还押金；流拍损失押金，货物退回；押金不重复扣；
- 分解/勘探/研磨把输入成本按产出数量分摊到产出批次；
- 账本缺失历史时记 `short_position`，不伪造成本；未入账数量在 `Holding` 里单独
  标成 `unknownQty`，不按零成本混入；
- 上架挂单从列表消失但既无成交事件也无邮件确认时，只标 `unobserved`，不记成交；
  终端的已实现、胜率、Alpha 衰减与决策校准只使用确认成交；
- 本地日志达到容量上限时，把最旧的前缀压缩成检查点（剩余批次、开仓挂单、
  `capital`、`cashAnchor`、`throughSeq`），再截断事件。`replay(检查点 + 事件)`
  必须与 `replay(全部事件)` 对持仓、开仓与资本给出相同结果；Lua 与 TypeScript
  两套重放共用同一组 fixture 做 parity；
- 金额是整数铜：商品的档位单价是 `总价 / 数量`，可以是小数，但挂单必须按整数铜
  上架（`Core.listPrice` 向下取整），账本投影里的成交单价、手续费与已实现盈亏也在
  两个运行时按同一规则取整，否则小数单价会让整次 Journal 导入在整数列上失败；
- 邮箱确认的成交如果对应一笔已推断的成交，写 `confirm` 原地升级该笔交易
  （补上真实手续费、清掉推断标记），而不是再记一次成交——否则同一笔钱会被
  记两遍，成本批次也会被消耗两遍。

桌面的 `src/lib/journal.ts` 用同一套规则重放，并有与 Lua 的 parity 测试。

### 2.5 邮箱成交采集

客户端只在邮箱里报告拍卖成交。`Mail.lua` 在 `MAIL_SHOW` / `MAIL_INBOX_UPDATE` 时读取
邮件表与拍卖发票（`GetInboxInvoiceInfo` 在 1.60 exe 中存在但未收录进生成文档，
`/wahdiag mail` 会打印原始字段供实测）。分类器同时使用 `invoice.kind` 与
“钱/物品”组合，区分成交、流拍、竞价赢得、取消返还和玩家邮件：

- 成交（钱、无退回物品）→ `sold` / `confirm`；
- 流拍（物、无钱、有发票）→ `expire`；
- 竞价赢得（有物品、有发票、已付款）→ `buy`，成本取发票的成交价；
- 取消返还（物品与押金同时退回）→ `cancel`（能定位原挂单时）或仅作为状态；
- 玩家邮件 → 只进入 estate 的 `mail` 位置，不记账。

成交翻译成 `sold` 事件，把带附件、无钱的退回邮件翻译成 `expire`：

- 归因顺序：附件链接 → 发票物品名/主题匹配扫描物品名 → 按总买断价唯一定位开仓挂单；
  都匹配不到就只计数、不写事件、也不记为已处理，绝不把成交记到猜测的物品上，
  后续扫描认识该物品时仍会补记；
- 数量 = 发票总价 / 挂单单价，能识别商品的部分成交；无挂单时按 1 件记；
- `inferred = false`，事件带 `listedAt`（挂单时间）与 `censored = true`（成交在开箱时才被观测）；
- 如果这笔成交在开箱前已经被在售对账推断过，写 `confirm` 升级那笔推断，不重复记账；
- 去重按指纹**计数**（`WoWDerhoiAH_MailSeen`，上限 500）：商品分批成交会产生多封
  主题、物品与金额完全相同的邮件，只有计数才能区分“同一封重复开箱”和“又一笔同价成交”；
  达到上限时只淘汰**不在本次收件箱里**的指纹——仍在收件箱的邮件必须保留计数，
  否则下次开箱会把同一笔成交再记一次；
- 任何账本写入（成交、买入、上架、撤单、制造、手动卖店/转移）都会合并成一次延迟
  落盘（`WAH.requestFlush`，约 2 秒）；扫描与开箱会立即 `WAH.flush` 并取消排队的那次，
  终端不必等到下一次拍卖扫描才看到账本变化；
- `/wahcapture mail off` 关闭采集：成交不再由邮箱确认，消失的挂单只标“未观测”，
  不记收入；`/wahcapture mail on` 恢复。
  `/wahdiag` 会打印两个采集开关的当前状态，关闭后已入账的记录保留不动。

同一物品多次成交的暴露时间按每笔挂单分别累计，而不是首末成交时间差：后者会把
“几笔挂单同时卖出”当成极短曝光，系统性高估成交速度。

### 2.6 SQLite / Prisma

- `Market`：只保留市场身份（realm+faction）、可空的开服时刻 `openedAt`
  （`/wahopen` 写入；`/wahopen auto` 会清空它）和最早观测 `firstScanAt`。
  现金、角色和背包空位不再属于市场，而是属于按角色分区的 `Estate`。
  `dataVersion` 是页面输入的提交令牌：导入事务在写入观测、状态、账本和计划的
  同一提交里递增它，打开的页面只轮询由它派生的版本号，因此失败的导入和
  被裁剪的诊断行都不会让页面误刷新。
- `MarketGeneration`：一次扫描一份不可变读模型，记录扫描时间、求值阶段、宽度、
  已下架数、`firstScanAt`、价格指数、共享核心输出与扫描缺口。页面只读这一代，
  不再在请求里重算市场。最近 2 代保留 signal rows 与核心输出供页面读取；盘口与扫描
  元数据保留最近 96 代（约一天，15 分钟扫描间隔），供 `npm run calibrate` 从相邻
  扫描的消失率校准成交先验。更早的代际连同 quotes 级联删除，旧代的核心输出替换为
  空求值，避免 JSON 无限累积。
- `MarketQuote`：这一代里每个物品的当前盘口（`AuctionSnapshot` 的全字段），不再承担历史。
  `priced = false` 标记纯需求行；价格统计只读 `priced = true`。行情历史在 `ItemSeries`，
  两边的寿命因此分开：删旧代际不会碰图表，折叠历史不会影响当前盘口。
- `MarketSignalRow`：这一代每个物品的物化信号，以及该物品在共享核心里的行（若通过门槛）。
  物品页只读自己的一行，不加载整个市场求值。
- `ItemSeries`：终端自己的插件序列副本，按物品存并行数组 `t/min/sell/q/n/e`。
  保留策略：最近 7 天全量、7–30 天每小时最后一个点、30–90 天每天最后一个点、
  更久每周一个点；事件点永远保留；单物品上限 4,000 点，超出等距折叠。
  插件升级会重建自己的文件，所以长历史必须由终端持有。
- `ImportRun`：每次导入一行（来源、扫描数、序列点数、quote 数、Journal 事件/错误、
  耗时、状态、错误信息）。健康页读最近 20 行；`/health` 也显示扫描缺口与序列覆盖。
- `Estate` / `EstateItem`：客户端推送的私有资产快照，按 `character:<name>` 或
  `account` 分区，每个分区带 `revision`、`observedAt`、`cash`、`freeSlots` 和
  `coverage`。`EstateItem.location` 区分 `carried / bank / account_bank / mail /
  listed / keyring`；未打开过的位置在 `coverage` 里是 `unobserved`，不是 0。
- `JournalBook`：每个 `(marketId, character, epoch)` 一行，记录本地分册存在。
  当前账本由最大 `epoch` 的标记决定，空分册也算数。
- `JournalFact`：追加式事实，按 `(marketId, character, epoch, seq)` 唯一。
  导入插入尚未存在的序号，并用同一序号的修正内容更新已存在的事实（不删除行）；
  同一分册的乱序重发是幂等的。`epoch` 是分册创建时刻，清除 SavedVariables 后
  新分册的序号重新从 1 开始，靠它区分。
- `LedgerCheckpoint`：本地日志截断前的前缀压缩状态，按 `(marketId, character,
  epoch, throughSeq)` 唯一。持仓、开仓与资本 = 最新 `epoch` 的检查点 + 之后的事实。
- `Holding`：按 `(marketId, character, itemId)` 的对账读模型，记录
  `qty / carriedQty / bankQty / accountBankQty / mailQty / listedQty /
  knownQty / unknownQty / missingQty / costBasis`。它由 `Estate` + 检查点 +
  `JournalFact` 派生，不是一次导入的整表替换。
- `Trade`：由 `JournalFact` 投影，追加而不整体重建。`observedAt`、`censored`
  随成交一起保存；`realizedAt` 是观测时间，区间
  `[listedAt, observedAt]` 才是成交真正发生的时间范围。`decisionId` 只在采纳
  归因时写入。
- `Decision`：由 `Plan` 写入一次（不是页面 GET），记录稳定 `decisionId`
  （`planRevision:item:kind`；`planRevision` 本身是
  `realm|faction|genEpoch:estateRevision:ledgerRevision:phase:character`，与插件 `/wahadopt`
  同一公式；计划修订只存在这个身份字符串里，不另设重复列）、
  阶段、行动类型、物品、理由与时间，以及预期净利、成交概率、
  成交依据、分配数量与成交价。预测字段只插入不更新；旧计划只标
  `supersededAt`。复盘优先按 `decisionId` 归因，未采纳的旧决策才退回同物品
  时间窗；校准用 `[listedAt, observedAt]` 做 censoring-aware 匹配，带成交
  概率的 `sell` 决策同样进入分桶。核心没有押金表时不伪造卖出成交率，该步骤
  只记录预期回款。少于 10 条决策的桶只显示“样本不足”。
- `Plan`：`Plan(generation, estate, ledger, config, now)` 的不可变输出，按
  `(marketId, revision)` 唯一，并记录铸造它的角色。`estateRevision` 属于该
  角色的 estate 分区，换角色后终端仍按同一角色的修订判断计划是否过期。
  `steps` 是资源可行的动作序列，`resources` 记录执行前后的现金与空位，
  `unplanned` 记录未纳入的动作及原因。计划还带铸造时的 `phase`：闸门和先验
  随阶段变化，扫描之后越过边界的计划必须按自己的阶段记录决策，而不是按扫描
  当时的阶段。游戏内是计划的铸造者；终端只存副本、历史与学习。
- `Recipe`：`data/recipes.forever.json` 的投影，导入时整体替换。
- 需求日历：唯一来源是 `src/data/events.json`，由 `gen:lua-rules` 编译成
  `WAH.EVENTS` 参与排序，首页“版本日历”也读同一份文件。`startsAt = 0` 的条目是模板，
  永远不会命中；未写 `endsAt` 表示瞬时事件，结束时间取 `startsAt`。

### 2.7 `WoWderhoiAH_Estate` 与对账

`Estate.lua` 是私有状态的唯一发布者。它监听 `BAG_UPDATE_DELAYED`、`PLAYER_MONEY`、
`BANKFRAME_OPENED` / `BANKFRAME_CLOSED`、`PLAYERBANKSLOTS_CHANGED`、
`PLAYER_ACCOUNT_BANK_TAB_SLOTS_CHANGED`、`PLAYER_ENTERING_WORLD`、
`OWNED_AUCTIONS_UPDATED` 与 `MAIL_INBOX_UPDATE`，把事件合并成 1–2 秒防抖后的一次
重算，只有快照真正变化才递增 `revision`。它导出独立的 `WoWderhoiAH_Estate`，
不塞进 `ScanData`：背包变化不应该伪造一次行情扫描。

扫描只更新它真正观测到的 `cash` 与 `freeSlots`，不改 `observedAt` 或 `revision`：
扫描不是一次 estate 观测，混用两个时钟会让扫描之后到达的、修订更新但观测时间更早
的 estate 文档被误判为旧文档。

`revision` 是单次插件安装内的本地计数器；重装插件或清除 SavedVariables 会让它
从 1 重新开始。终端因此以 `observedAt` 判断新旧：观测时间更晚的文档即使计数器更小
也接受（重装后的新状态），观测时间更早的文档即使计数器更大也丢弃（延迟到达的旧
状态）；同一秒内则只有更大的计数器才是更新。同一个计数器但观测时间更晚，说明
重装后的首个文档恰好撞上了旧计数器，也要接受；真正的重发会沿用旧的观测时间。
唯一例外是扫描创建的“只有现金与空位”的种子行：真正的 estate 文档可以带着更早的
观测时间替换它。

覆盖范围与语义：

- 背包 0–4、材料包 5、钥匙链 -1、角色银行 6–14、账号银行 15–23；
- `carried` 与 `money` 在登录后即可信；
- 角色银行在 `BANKFRAME_OPENED` 之后标 `observed`；账号银行只有 15–23 号容器真的
  报告槽位时才标 `observed`，页签不存在或客户端没有暴露它不等于空账号银行；
- 邮箱只在 `MAIL_INBOX_UPDATE` 之后标 `observed`；`MAIL_SHOW` 发生在收件箱加载之前，
  只触发重建，不能证明已经读到邮件；
- 在售只在 `OWNED_AUCTIONS_UPDATED` 之后标 `observed`；
- 银行或邮箱关闭后保留最后一次观测；之后的事件重建不会把不可读的容器当成空的，
  一次没有暴露账号银行页签的开银行也不会清掉上一次读到的账号银行；
- 未观测位置不参与 `missingQty` 判定；
- 每个分区只保存自己负责的位置：`carried / bank / mail / keyring` 属于角色分区，
  `account_bank / listed` 属于 `account` 分区。终端拒绝跨分区的条目、未知的
  coverage 键或值，以及缺少 `observedAt` 或 `revision` 的文档——静默降级会把
  发布端的错误藏进一个看似合理的状态里。

`Reconciler.lua` 在插件侧为游戏内估值完成对账，因为只有插件同时拥有实时
estate、账本和在售列表。终端导入 `Estate` 与 `JournalFact` 后用同一组规则重算
`Holding`，让跨角色页面读到一个持久化结果：

```text
knownQty   = min(ledgerQty, totalQty)
unknownQty = max(0, totalQty - ledgerQty)   -- 装插件前、拾取、邮件等未入账
missingQty = max(0, ledgerQty - observedQty) -- 仅对已观测位置计算
expectedCash = cashAnchor + cashDelta
unexplained  = GetMoney() - expectedCash
```

`unknownQty` 的成本为空，不按 0 混入浮动盈亏。`sellable = carriedQty`；背包为空
而银行有货时，`sellable` 取银行数量并标 `requiresBank`，卖出计划把去银行取货
作为该步骤的前置条件。在售单位（`listed`）仍属于持仓，但不再进入卖出数量。

## 3. 算法

信号层把最近一次扫描代际当作“当前簿”：只有在该次扫描中仍有正价挂单的物品
（`stale = false`）会进入共享核心、行动清单与预警；未出现在该代际的物品仍保留在
`signals` 里供市场表和物品页查看，并标为“已下架”，价格是上次有货时的值。游戏内雷达
只评估当前扫描，终端因此与它描述同一本书——不会拿一件早已卖光的物品的历史报价去推荐买入。

### 3.1 三个价格

- `minP`：当前可买最低单价。
- `sellP`：深度感知卖价前沿。先算数量加权中位，剔除高于中位 3 倍的噪声挂单；
  再取累计数量达到 `q* = max(1, ceil(0.03Q), qmin)` 的最低价位。商品按数量累计，
  物品拍卖按笔数取第 `min(3, N)` 便宜的一口价。点火期 `qmin=1`，之后为 3。
- `listP = max(vendorP + 1, sellP - 1)`。

### 3.2 三层数量与阶梯成本

同一本书上的“数量”有三个不同含义，名字必须分开：

| 名称 | 含义 | 使用场景 |
|---|---|---|
| `quantity` | 扫描到的全部在售数量，不受预算约束 | 供给统计、成交率分母 |
| `candidateQty` | 在价格上限、背包容量和**整笔请求预算**下能买到的数量 | 排序与门槛，标注“全预算可执行” |
| `allocQty` | 所有行共享一笔钱包后实际分到的数量 | 所有“现在能买”的视图，标注“已分配” |

```text
C(n) = Σ_j min(remaining, q_j) · p_j
pCap = listP · (1 − fee) − minUnitProfit
Qcandidate = min(供给(p ≤ pCap), floor(预算 / 均价), 背包容量)
```

`candidateQty` 与对应的 `candidateNet`、`candidateNetPerUnit`、`candidateUnitPrice`
只描述“整笔预算下盘口有多深”，用于排序与门槛，不能作为“这笔交易赚多少”的承诺。
任何承诺“现在能买”的视图必须使用 `allocQty`、`allocUnitPrice`、`allocNet`；
同一行不允许数量取一层、净利取另一层。雷达的净利列、终端的“可执行机会”和
“预算内分配”都遵循这条规则。

预算本身以客户端状态里的现金为上限：`effectiveBudget = min(规划预算, 现金)`。
现金来自 Estate（实时推送，尚未推送时由最近扫描的 `cash` 播种）；只有现金
**未上报**（`nil`，例如旧载荷）时才完全使用规划预算；上报的 `0` 是空钱包，
不资助任何交易。终端把这个上限同样用于凯利仓位与制造 LP，所以“可执行机会”、
“仓位建议”和“制造计划”不会引用两笔不同的本金。

### 3.3 手续费、押金与保本

```text
售出净利 = listP · qty · (1 − fee) − 成本
售出保本 = 单位成本 / (1 − fee)
流拍保本 = (成本 + 押金) / (qty · (1 − fee))
流拍最坏损失 = 押金 + max(0, 成本 − NPC 保底残值)
```

流拍后货物退回，所以损失是押金加上“成本高于 NPC 保底价”的差额，不是整批成本。

押金成交退还，只有流拍/撤单才损失。手续费默认 5%，可通过规则源修改；中立拍卖行
15% 尚未单独建模。

**价格 × 时长搜索**：卖出页在挂单价 `listPrice`（`sellP` 压 1 铜，且不低于 NPC 价 + 1）及其 98%、95% 与 12/24/48 小时中，最大化
`净利 × P(成交) − 押金 × P(流拍)`；`P(成交)` 用队列模型
`1 − exp(−h · supply · T / (前方供给 + qty))`，押金取客户端三档返回值，候选价永不
低于 NPC 价 + 1。只有 `fillBasis` 不是 `prior`（有该物品自己的成交或可观测消失）时
才启用；`/wahpricing off` 退回“卖价前沿减 1 铜 + 所选时长”。终端不展示押金优化——
它调不到客户端押金接口，给出游戏里做不到的方案没有意义。

### 3.4 成交概率

```text
P(fill ≤ T) = 1 − exp(−h · supply · T / (ahead + qty))
```

`h` 是**整本书每小时成交份额**，也是校准脚本测量的单位；`supply` 是在售件数，
`ahead` 是排在挂单前面的件数，`qty` 是挂单件数。雷达、终端图表和卖出页都调用
同一个 `Core.fillWithin`：把份额直接当成挂单级 hazard 再乘一次 `qty/(ahead+qty)`，
会让同一物品在雷达和卖出页显示两个成交率。

两种队列口径的区别只在于货从哪里来：

- **从背包上架**（卖出页与终端图表）：盘口不变，`ahead` 就是价位及以下的全部在售量。
- **买入后再挂回**（雷达）：`qty` 件先从盘口被买走，`ahead = max(0, 价位及以下在售量 − qty)`
  ——没被买走的那部分才排在你前面。

`h` 按证据等级选择，输出同时带 `fillBasis`：

| 等级 | 条件 | `h`（份额/小时） | 含义 |
|---|---|---|---|
| `own` | 自己的成交 ≥ 3 笔 | `(ownSold / ownExposedHours) / supply` | 唯一干净标签；暴露时间按每笔挂单累计 |
| `proxy` | 可观测且有公共推断消失 | `(h₀·P + sold) / (P + supply · elapsed)` | 用区间下沿；上沿含换价重挂，不能当成交 |
| `observed-zero` | 可观测、供给非零、消失为零 | 同上，`sold = 0` | **零观测是证据**：慢物品的后验应被压低，不是回退到先验 |
| `prior` | 观测不可用 | 阶段 × 市场类型基线 | 开服冷启动的结构先验 |

“可观测”有两个条件，缺一不可：owner 可见（`ownerVisible = true` 且
`sellersInvisible = false`），并且**这次扫描有这个物品的上一轮 capture**
（`flowObserved = true`）。首次扫描、升级后第一轮、以及两次扫描之间才被上架的物品都没有
基线，消失区间为 0 是缺失数据而不是零观测——否则每一次首扫都会把整市场的成交率收缩到
接近零，校准也会把这些假零当成样本。

没有 `supply` 时不存在队列，份额退化为直接作用于挂单本身
（`1 − exp(−h · T)`），这是同一数字的保守读法，只用于拿不到盘口规模的调用方。

`h₀` 与先验强度 `P`（默认 50 单位·小时）来自 `src/lib/market-rules.ts` 的
`fillPrior`，编译进 `WAH.RULES.fillPrior`；核心不再自带一份数字。`proxy` 与
`observed-zero` 用 Gamma–Poisson 收缩：盘口越大、观测越久，先验权重越小。
`npm run calibrate` 只读当前 `OBSERVATION_VERSION` 及以上、卖家完全可见
（`sellersInvisible = false`）且 `flowObserved = true` 的 quote：owner 隐藏或没有上一轮基线时
下沿恒为 0，那是缺失数据，不是零成交，学进去会把先验压向零。该标记出现之前导入的行按
导入时的行为视为已观测（`flowObserved = true`）。阶段与宽度按**那次扫描的整个市场**判定（每个时间戳的在售种类数、
市场最早扫描或开服锚点），不是按单个物品的首次出现。输出按阶段 × 市场类型的中位数与
四分位；样本不足 500 条时只打印“样本不足”，脚本从不改规则文件——人审后改 `fillPrior`
再重新生成。

样本少于 3 时自己的成交不算证据；三种等级都输出 `[low, high]` 区间，界面标注来源。
`own` 来自 Journal 的 `sold` 事件（近 7 天，`inferred = false`，只算拍卖行渠道）。曝光
小时是每笔成交各自 `max(观测时间 − 挂单时间, 扫描间隔)` 之和，不是首末成交的跨度：
几笔挂单在同一小时内卖出时，后者会把曝光压到一个扫描间隔，直接放大成交率。桌面端
从 `Trade` 表用完全相同的过滤条件与公式重建，游戏内与终端输入同一形状。

核心同时返回 `h` 本身（`fillHazard`），图表的价格—成交曲线直接以它为锚，不再从
`fillProb` 反推：在长窗口下 `h` 被上限截断时，`fillProb` 会舍入成 1，反推会得到
“没有估计”。曲线越往高价、前方供给越多，成交概率越低；区间带取自核心的
`fillProbLow/fillProbHigh`，不是图表自己的常数。

### 3.5 阶段

```text
phase = ignition  if age < 6h  or breadth < 80
        wave      if age < 48h or breadth < 400
        settle    if age < 168h or breadth < 800
        steady    otherwise
```

`breadth` 是最近一次扫描中有正价的物品种类数：已下架物品保留历史，但不再计入市场宽度。
`/wahphase` 可手动覆盖；桌面用 `AQT_PHASE` 覆盖。**导入时**按 `openedAt ?? firstScanAt`
把年龄和这一代的 breadth 代入规则，结果写进 `MarketGeneration.phase`，共享核心就在这个
阶段下求值。页面读取时再按真实时钟重算“显示阶段”：跨过边界时，旧代际的行动清单收起并
提示需要重新扫描，而不是拿新阶段的门槛去套旧盘口。核心不会用单次扫描窗口重新推算阶段，
否则活跃市场会因为“最近一次扫描是几分钟前”而被永久判成点火期。阶段决定历史窗口、样本
门槛、价差窗口与净利门槛：

| 类型 | 点火期 | 洪流期 | 沉淀期 | 稳态 |
|---|---|---|---|---|
| vendor | NPC 必买，不经门槛 | 同左 | 同左 | 同左 |
| commodity 价差 | 20–85% | 12–60% | 8–50% | 6–40% |
| item 价差 | 25–80% | 18–70% | 15–60% | 12–50% |
| commodity 挂单/卖家 | 1/1 | 3/2 | 5/3 | 8/4 |
| item 挂单 | 1 | 2 | 3 | 3 |

净利与单价利润门槛见 `src/lib/market-rules.ts`；它是唯一事实源，编译到
`GeneratedRules.lua`，漂移测试保证两边一致。

### 3.6 排序

- 点火期：NPC 套利 > 净利 × 成交率 × **需求先验**（存在竞价时先验 ×1.2，事件窗口再乘事件权重）；
- 洪流期：净利 × 成交率 / max(供给增速, 0.1)；
- 沉淀/稳态：净利 × 成交率 × 置信度。

三项修正叠加在排序分上，不改变门槛：**卖家集中度**（`1 − 0.15 × HHI`，只在 owner
可见时生效）、**时间成本**（除以“拍卖行往返 + 买入”的预计分钟数）、以及需求事件
（`src/data/events.json` 编译进 `WAH.EVENTS`，只缩放排序先验；未写 `endsAt` 表示瞬时
事件，结束时间取 `startsAt`，结束早于开始会直接报错）。每行与每条行动都给出
`netPerMinute`（买入计“往返 + 买入”，上架计“往返 + 上架”），游戏内行动提示框与终端
行动清单显示同一个努力调整后的收益。

竞价是客户端唯一直接暴露的需求信号：`highestBid > 0` 只在点火期抬高排序权重，
不放松任何门槛，也不进入置信度。之后按排序做一次共享预算分配（见 3.8）。

需求先验来自 `src/data/demand-bands.json`：背包、魔杖、药水、食物、弹药、附魔材料在
开服前段权重更高；护甲等分散需求权重更低；未匹配为 1.0。同一张表编译到
`GeneratedRules.lua` 的 `WAH.DEMAND`，游戏内与终端共用。它只在点火期参与排序，
有了自己的成交后由成交率接管。

NPC 套利永远第一：它没有市场风险，只有预算和背包约束。

上述排序只决定候选行。计划层再把买入与卖出放进同一个货币（增量金币/分钟）做
一次全序：

- 买入：`增量 = 预期收入 − 成本 − 手续费`；
- 卖出：`增量 = 回款 − 手续费`；历史成本**不进入排序**，只输出 `realizedPnl` 与
  `costKnown`。成本未知的物品不会因为“零成本”被推到最前，亏损品也不会因为沉没
  成本被排到最后；
- 排序键为 `netPerMinute` 降序、`itemId` 升序、`kind` 兜底；同一物品在不同成本下
  只要卖价相同，排序相同；
- 计划从 `estate.cash` 与 `estate.freeSlots` 出发逐条排入；买入被现金或空位挡住时，
  把尚未排入的卖出步骤提升到它前面，用回款和释放的空位继续。每一步记录执行前后的
  现金与空位，不能出现“12 条买入各自占用整个背包”的不可行计划。

### 3.7 生产网络

```text
max_x (pᵀA − cᵀ) x   s.t. Bx ≤ b, x ≥ 0
```

- 变量：每条配方的制造次数；
- 目标：成品建议卖价 × 数量 × (1 − 手续费) − 材料成本；材料按当前建议卖价计成本，
  没有在售行情的材料不猜价，该配方计入“缺少价格数据”；
- 约束：每专业每日制造次数、材料在售量、预算（`min(规划预算, 现金)`；
  现金为 0 时预算约束为 0，计划为空）；
- 对偶变量：影子价格——多一个产能单位值多少金币；
- 小规模稠密单纯形；候选先按单件净利截断到 120 条；LP 解向下取整，净利按整数
  计划重算；求解失败时回退到贪心并在界面标注。

配方数据来自「无限图鉴 wuxianwow.com」的 1.60 客户端导出，共 2,595 条（1,147 条
1.60 新增），含权威材料与产物 itemId。产能是终端配置，不是客户端事实。

游戏内另有一份只含材料的编译表 `GeneratedRecipes.lua`（`npm run recipes:lua` 生成，
约 154 KB）：`Craft.lua` 监听 `TRADE_SKILL_CRAFT_BEGIN` 与
`TRADE_SKILL_ITEM_CRAFTED_RESULT`，把制造写成带产物、数量与 `mats` 的 `craft` 事件。
配方 id 先按 spell id 查，再按 `C_TradeSkillUI.GetRecipeInfo().recipeID` 查，最后按
“唯一产物”回退；都不中记 `craft_unmapped`，不写账本——宁可少记，不可把成本记到错配方上。

### 3.8 组合与仓位

```text
f* = p − (1 − p) / b,  b = 盈利 / 亏损
盈利 = 挂单价 · (1 − 手续费) − 入场价
亏损 = 当前价差（建议卖价 − 最低价）
仓位 = kappa · f*，再受单物品敞口与日预算约束
```

仓位按**入场价**（盘口最低价）估算，不按全深度均价：均价贴着价格上限，会让每一本深盘
看起来“只赚一个单位下限、却亏掉整笔本金”，Kelly 在任何真实成交率下都把每一行压成 0
（游戏内表现为「可买」全是 0）。分配后仍按实际吃到的档位重新计价，所以雷达上的数量、
买价与净利描述同一笔交易，估算价只是下注规模的基准。

亏损取一段价差，而不是“单位成本 − 残值”：流拍后货物退回，风险是一段逆向价格波动，
不是整批成本归零；用整批成本当亏损，等于把每次进货都当作全损赌博。样本不足
时标 `exploratory`，不把先验成交率当成估计出来的概率。

门槛与凯利必须对同一边际达成一致。`Core.evaluate` 在构造候选行之前调用同一个
`Core.sizePosition`：凯利比例为零的行计入 `diagnostics.excluded.sizing`，不进入
`rows`。因此“通过门槛的行”天然是风险模型愿意开仓的行，零分配只可能来自钱包、
单物品敞口或盘口，而不是“门槛放行、风险模型否决”的错位。

分配在共享核心的 `Core.allocate` 里完成，游戏内与终端跑同一份：按已排好的行依次分配，
`remaining = min(预算, 现金) × dailyBudget`，每行的数量取 Kelly 预算与剩余预算**沿盘口
阶梯实际能吃到的数量**，并以 `candidateQty` 为上限，只减不增。不能拿“预算 ÷ 全深度均价”
换算数量：前段便宜、后段昂贵的盘口（10 件 100 铜、100 件 1,000 铜）会被均价严重低估，
同样的预算本可买下十件，却只算出两件。`candidateQty` 只表示全预算可执行量；同一行的
数量与利润必须描述同一笔交易。分配后的数量会按盘口从最低价重新计价（`allocCost`），
因为少买只会吃到便宜的档位；沿用全深度均价会同时低估利润、高估占用资金。

`Core.allocate` 只产生两个输出：每条候选行的 `unfunded` 原因
（`kelly | exposure | purse | depth`；`kelly` 只在直接以未筛行调用 `allocate` 时出现，
`evaluate` 已把零比例行计入 `excluded.sizing`）与汇总的 `diagnostics.unfunded`；真正得到铜板的行
组成 `output.opportunities`。游戏内雷达、终端“可执行机会”和“预算内分配”只渲染
`opportunities`，空态必须引用 `diagnostics` 说明具体原因，不得把所有零分配都解释成
钱包不足。

买入行动的 `maxUnitPrice` 与 `stop.ifPriceAbove` 复用门槛的同一个单价上限
`listP · (1 − fee) − minUnitProfit`（向下取整到铜），而不是盈亏平衡价
`listP · (1 − fee)`。否则条件单会在价格上移后接受一个单位净利已跌破门槛的价位，
计划与门槛就描述了两个不同的边际。

背包容量与现金一样是共享资源：`Core.allocate` 的 `remainingSlots` 从当前空位加上
计划卖出将腾出的单位数开始，随每个买入行递减，每行拿到的数量同时受 `candidateQty`、
剩余现金与剩余空位约束；计划走查在背包满时会先放入卖出步骤，再用它释放的空间和
回款执行买入。同一物品的既有持仓（含成本未知部分）计入单物品敞口上限，避免
“已经有 50 件还按全额现金再买一堆”。

`bagSlots × stackSize` 是容量上界的保守近似：`stackSize` 固定为编译常量 20，按每件
物品都能堆满计算，物品实际堆叠更小时会高估能放下的数量。按候选物品读取真实堆叠
会为每行增加一次 `GetItemInfo`，而预算与盘口深度通常先成为约束，所以这里刻意保留
常量近似。

### 3.9 学习与校准

- **离策略评估**：把决策与后续成交按物品和时间窗口匹配，按倾向加权，报告覆盖率与
  有效样本量。倾向为 1 时它退化为描述性匹配，界面明确说明“不是因果效应”。
- **Alpha 衰减**：按周分桶的胜率与确认成交的已实现 P&L；未观测消失和成本未知的
  部分单列，不进入校准。最近窗口胜率下降 15 个百分点，或连续两个正窗口后转负，
  触发提示。
- **受控实验**：围绕建议卖价设计 2–5 个价位的小批量挂单；复盘页按物品 + 实际成交单价
  把确认成交与 `listedAt` 配对，报告成交笔数、件数与中位成交时长。价位取自成交记录本身，
  不取按当天卖价重算的计划——卖价前沿移动后，旧计划价位会把已成交的档位显示成未成交。
  未成交挂单没有持久化，所以不计算成交率——没有成交就显示“未成交”，不显示 0%；
  结论只用于调整下一轮价位，不直接改全局阈值。

### 3.10 宏观 deflate

```text
p_real(t) = p(t) / P(t) · 100
```

`P(t)` 是每日全市场物品建议卖价的中位，归一化到第一个有数据的日子。缺失日沿用上一
个观测值，不插值。跨天比较用真实价格；同一天内用名义价格。

## 4. 单一决策核心

`addon/WoWderhoiAH/Core.lua` 是唯一实现：

- 无 WoW API，Lua 5.1 兼容，输入输出都是普通表；
- 游戏内由 `WAH.coreInput()` 组装输入；
- 桌面由 `src/lib/core/from-market.ts` 用同一形状组装，经 fengari 运行；
- `addon/test/core-parity.test.ts` 对比两条加载路径的输出。

`Trade.lua`、`Sell.lua` 和终端页面都只渲染 Core 的输出，不重新实现定价或排序。

## 5. 运行边界

- 客户端没有成交历史接口；公共成交不可观测。
- `GetBids` / `QueryBids` 只覆盖玩家自己的竞价，不是全市场买单。
- `GetReplicateItemTimeLeft` 可能返回秒或档位；`/wahdiag` 实测并降级。
- `PostItem` / `PostCommodity` / `CancelAuction` 带 `HasRestrictions`；被拦截时
  降级为手动价格助手，不重试、不假装成功。
- 插件不做全自动扫货或上架；每次购买与上架都经过客户端确认。
- 公共捡漏/低吸/高抛视图已经商品化；优势来自执行、私有成交、产能与资本配置。

## 6. 验收清单

1. 第一次扫描写入 v4：盘口、卖家、到期桶、竞价、扫描龄、可选开服时刻。
2. 买 → 挂 → 成交/流拍闭环可重放，P&L 与金币变化一致（误差 = 手续费 + 押金）。
3. 邮箱成交写入 `inferred = false` 的 `sold`；若该笔此前已被推断，则写 `confirm` 升级，
   同一笔成交只记一次账；重复开箱不重复记账；成交率按暴露时间估计。
4. 制造写入 `craft`，产物成本等于材料 FIFO 账面成本；材料未入账时标短头寸，不静默记零。
5. 雷达每行有可买数量（`allocQty`）、买价（`allocUnitPrice`）、建议卖价、净利
   （`allocNet`）、成交率；数量与净利必须来自同一层。
6. 所有百分比带分母与窗口；P10 只出现在统计区。
7. 图表 0/1/2 点时显示盘口，不显示空框。
8. 卖出页算押金、售出/流拍保本价，被拦截时降级。
9. 同一扫描，Lua 与 fengari 输出一致；`opportunities`、未资助原因与终端行动清单数量一致。
10. 背包空位来自客户端；`/wahopen` 后阶段按开服时刻推进。
11. 配方网络可导入、可求解，影子价格可见，退化有标注。
12. 性能门禁通过；`/wahdiag` 每项都有结论。
13. 雷达或终端机会面板为空时，必须说明原因：无门槛候选、风险仓位拒绝、钱包不足、
    单物品敞口或盘口不足，不得把所有零分配写成“钱包不够”。
14. 同一搜索夹具在 Lua 与 TypeScript 中得到相同顺序；连续输入时只有最新查询的结果
    会被打开。
15. `/wahdiag` 分别给出 wait / api / lua / finish / save 与各自占比。
16. 扫描载荷门槛断言 SavedVariables 的真实 JSON 体积；收尾阶段分帧，单帧不超过预算。
17. 原生 UI 的买入、上架、成交、取消、过期各记一次；取消不会产生假成交。
18. 角色 A 与 B 的持仓、现金、成交同时存在；导入 B 不删除 A 的数据，也不拿 B 的
    现金给 A 的计划定尺寸。
19. 背包变化在防抖与 watcher 轮询预算内到达终端；游戏内雷达即时。
20. 对账闭合：`knownQty + unknownQty + missingQty` 与各已观测位置数量一致；
    未观测位置不被当成 0。
21. 计划可行：每一步的现金与空位都来自前一步之后的可用量；卖出回款参与买入预算。
22. 计划排序与成本无关：同一物品的成本 800、成本未知、成本 1200 三种情况下，
    只要卖价相同，排序相同；`realizedPnl` 单列展示。
23. 买入候选足够多时，卖出步骤仍可见且排在正确位置。
24. 同一 `decisionId` 的预测不再变化；采纳指向确切的 `planRevision`；
    延迟开邮箱的成交不会被排除在预测窗口外；带成交概率的卖出决策进入校准，
    没有押金数据时核心不伪造这个概率。
